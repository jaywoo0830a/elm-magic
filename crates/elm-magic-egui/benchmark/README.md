# elm-magic-egui 벤치마크 — 측정과 병목 귀속

> **한 줄 요약**: 같은 화면(1,000행 목록 = 3,005노드)을 **손으로 쓴 egui**로 그리면
> 1.11ms, elm-magic 어댑터(앱 경로 `render_fast`)는 2.81ms — **2.5배**다.
> 이 문서는 그 1.7ms가 **어디서** 나오는지 단계(P)·핫스팟(H)·단가(H8)로 귀속하고,
> 실제로 줄인 것(0.8.3 → 다음 릴리스: **-31%**)과 남은 후보를 기록한다.

## 0. 실행

```bash
# 한 줄로 전부 (루트에서)
bash ./bench                      # 기본 크기(100 / 1,000 / 3,000행)로 모든 표
bash ./bench 1000                 # 그 크기만
bash ./bench --quick              # 작은 크기(100행)로 빠르게
bash ./bench --perf              # benchmark_guard의 시간 예산 단언까지
bash ./bench --out perf.md        # 결과를 파일로 (붙여넣기용)

# 개별 실행 (같은 일을 손으로)
cargo test -p elm-magic-egui --test benchmark_phases    --release -- --nocapture
cargo test -p elm-magic-egui --test benchmark_baselines --release -- --nocapture
cargo test -p elm-magic-egui --test benchmark_hotspots  --release -- --nocapture --test-threads=1
cargo test -p elm-magic-egui --test benchmark_rules     --release -- --nocapture
cargo test -p elm-magic-egui --test benchmark_state     --release -- --nocapture
cargo test -p elm-magic-egui --test benchmark_guard     --release -- --nocapture

# 트리 크기 지정 (기본 100,1000,3000 — 환경변수가 인자보다 우선한다)
ELM_MAGIC_BENCH_N=100,1000,3000 bash ./bench

# 시간 회귀 단언을 켠다 (기본은 꺼짐 — 벽시계는 CI에서 flaky)
ELM_MAGIC_PERF=1 bash ./bench --guard
```

`bash ./bench`는 릴리스 빌드 후 6개 타깃을 순서대로 돌리고 진행 로그만 걷어내 찍는다.
`crates/elm-magic-egui/benchmark/run.sh`도 같은 스크립트를 부른다(디렉터리 안에서
바로 돌릴 때). `cargo test`가 이 파일들을 컴파일하되 **돌리지 않게** 하는 이유:
Cargo의 자동 탐색은 `tests/`만 보므로 `benchmark/`는 `Cargo.toml`의 `[[test]]`로
명시 등록돼 있고, 각 측정은 본문이 테스트 함수라 계약 스위트에 섞이지 않는다.

| 파일 | 재는 것 |
|---|---|
| `harness.rs` | 공용 하네스 — 참조 컴포넌트/`css!`, 트리 순회, 시간 통계, 페인트 명령 히스토그램 |
| `phases.rs` | **단계 분해** P0~P5 (egui 바닥 / 트리 재생성 / 스타일 해석 / 어댑터(기록O) / 어댑터 앱경로 / 테셀레이션) |
| `baselines.rs` | **손 egui 기준선** B1(naive) B2(tuned) vs B3/B4(어댑터) + 페인트 명령 수 |
| `hotspots.rs` | **병목 후보별 분리 측정** H1~H8 (H8 = egui 조작 단가표) |
| `rules.rs` | **규칙 수 스윕**(H2) — 자기 프로세스에서 레지스트리를 비우고 채운다 |
| `state.rs` | **상태 추적 게이트** — `:hover` 규칙이 없으면 안 읽고, 있으면 읽는지 (양방향) |
| `guard.rs` | **회귀 가드** — 벽시계에 기대지 않는 불변식 + 옵트인 시간 예산 |

## 1. 측정 규약 (왜 이 숫자를 믿을 수 있는가)

- **헤드리스**: `egui::Context::run_ui`로 창·GPU 없이 돈다(`tests/adapter.rs`와 같은
  하네스). `run_ui`는 뷰포트 전체를 덮는 루트 `Ui`를 준다 — 패널/프레임을 하나 덜 만든다.
- **릴리스 전용**: `cfg!(debug_assertions)`면 각 측정이 `SKIP`을 찍는다.
- **워밍업**: 폰트 아틀라스·갈레이 캐시·egui 메모리를 채운 뒤 잰다. 측정 구간은
  `Instant` 벽시계이며 **최소/중위/p90**만 보고한다(최소 = 노이즈 바닥, 중위 = 대표값,
  p90 = 꼬리). 이 문서의 표는 중위값이며, 노이즈가 큰 항목은 최소값도 함께 적는다.
- **페인트 명령(GPU 이전)**: `Context::tessellate`까지 잰다. 실제 래스터라이저는 없다.
- **CI**: 시간 단언은 `ELM_MAGIC_PERF=1`일 때만. 기본 CI는 `guard.rs`의 **구조 불변식**만
  본다(트리 모양 3n+5, 노드당 스타일 기록 1개 이하, 프레임 반복 시 egui temp data 불변).

## 2. 참조 트리 — 벤치 수치의 의미

`harness.rs`의 `BenchList`는 **실제 앱과 같은 모양**을 노린다:

```rust
<Col class="bench_root">                       // 패딩/갭
  <Row class="bench_head"> … </Row>            // 머리 행(텍스트 + 버튼)
  <For each={items.clone()} as={t} key={t.id}> // keyed 슬롯
    <Row class="bench_row">                    // height/gap/padding
      <Text class="bench_row_text">{t.label.clone()}</Text>  // flex-grow: 1
      <Button class="bench_btn">"x"</Button>
    </Row>
  </For>
</Col>
```

- 노드 수 = **3n + 5** (행 1개 = `Row` + `Text` + `Button`), `guard.rs`가 계약으로 고정한다.
- `css!` 규칙은 6개(실제 앱은 20~60개) — 규칙 수의 영향은 `rules.rs`가 따로 스윕한다.
- `PlainList`(클래스 없음) / `ClassedList`(같은 모양 + 클래스) / `DeepCol`(깊이 중첩) /
  `BenchListPositional`(key 없음)이 비교군이다.

## 3. 예측 vs 실측 — 정적 분석으로 세운 가설 채점

벤치마크를 만들기 **전에** 코드만 읽고 세운 추정이다(측정으로 검증·반증한다):

| # | 가설(정적 분석) | 예측치 | 실측 | 판정 |
|---|---|---|---|---|
| 1 | 스타일 해석이 지배한다 — 호출마다 전역 등록부를 훑어 `O(등록 규칙)` | 노드당 1.5~3µs × 3~5회 | 규칙 6개에서 **70ns/회**(H1), **규칙당 5.2ns로 정확히 선형**(H2) → 3,005노드×3회 = 0.21ms | **규칙이 적으면 아니다.** 규칙 200개면 약 9ms → **큰 앱에서는 지배한다** |
| 2 | intrinsic 예산 계산이 자식 트리를 다시 돌아 `O(N×깊이)` | 초선형 | 깊이 중첩이 평면보다 **노드당 0.67~0.73배**(H3) | **반증.** 재순회는 있지만 컨테이너 순회 단가가 ~10ns라 무해 |
| 3 | 텍스트 측정(갈레이)이 노드당 2회(예산 + 그리기) | 행당 ~1µs | `Label` 288ns(H8) + intrinsic 측정 ~300ns → **행당 약 600ns** | **맞음** (전체의 약 26%) |
| 4 | 노드마다 egui temp data 왕복(get+insert)이 비싸다 | 노드당 200~300ns | **37ns/노드**(H6), 3,005노드 0.11ms = 전체의 **3%** | **틀림** (egui 로컬 해시가 매우 싸다) |
| 5 | `Pass.styles`가 노드마다 `ResolvedStyle`을 복제해 쌓는다 | 1.8MB/프레임 | 복제 **3,004회**, `render` vs `render_fast` = **+0.77ms (22%)** (H7·B4) | **맞음** → 옵트아웃 도입 |
| 6 | 트리 재생성(매 프레임 전체 재구성)이 지배한다 | 전체의 60%+ | **0.56ms = 13%** (P1) — keyed 슬롯이 +6% (H4) | **과대평가** |
| 7 | 손 egui 대비 오버헤드 | 10~40배 | 최적화 전 **3.6배**, 후 **2.5배** (B1/B3) | **과대평가** |
| 8 | 1만 노드대에서 60fps 예산을 넘는다 | 50~150ms | 9,005노드(3,000행) **13.0ms** (render_fast) → 60fps 경계 | **대체로 맞음** (예측이 더 비관적) |

**교훈**: "매 프레임 트리를 다시 만들고 스타일을 다시 해석한다"는 구조적 직관은
방향은 맞지만 **크기를 크게 과대평가**했다. 실제 지배 항은 (a) 규칙 수 × 노드 수 × 호출 수,
(b) 텍스트 측정, (c) 기록(Pass) 복제, 그리고 (d) **노드마다 만드는 egui `Ui` 조작 수**였다.

## 4. 실측 — 단계 분해 (`phases.rs`)

중위값(ms). `P3`는 기록 포함(테스트 경로), `P4`는 `render_fast`(앱 경로).

| 단계 | N=100 (305노드) | N=1000 (3005노드) | N=3000 (9005노드) |
|---|---|---|---|
| P0 egui 빈 패스 | 0.001 | 0.001 | 0.001 |
| P1 트리 재생성 | 0.059 | 0.560 | 1.684 |
| P2 스타일 해석 1회/노드 | 0.022 | 0.212 | 0.635 |
| P3 어댑터(+기록) | 0.295 | 2.920 | 8.814 |
| **P4 어댑터(app 경로)** | **0.281** | **2.784** | **8.362** |
| P5 테셀레이션 | 0.005 | 0.019 | 0.049 |

(한 번의 `bash ./bench` 실행에서 나온 중위값, 조용한 머신. P3는 `Pass.styles` 복제
(노드마다 수백 바이트) 때문에 실행 간 편차가 더 크다 — P4는 ±1%로 안정적이다.)

- `P3/(P1+P2)` = **3.7~3.8배** (최적화 전 4.5~7.5배) → 어댑터는 자기
  파이프라인(트리+해석)보다 **egui 위젯 조작**에 여전히 3~4배를 쓴다.
- `render_fast`가 절약한 양: N=100 0.014ms, N=1000 0.136ms(-5%),
  N=3000 0.45ms(-5%) — 기록 비용은 노드 수에 선형이다.
- 60fps(16.6ms) 여유: N=1000 → **359fps**, N=3000 → **119fps** (최적화 전 74fps).
- 크기 선형성: 3,000행 P4 = 8.36ms ≈ 1,000행 × 3 (8.35ms) — 캐시 할당 재사용으로
  3,000행에서의 초선형(페이지 폴트) 항을 없앴다.

## 5. 실측 — 손 egui 기준선 (`baselines.rs`)

| 기준선 | N=100 | N=1000 | N=3000 | 페인트 명령(1,000행) |
|---|---|---|---|---|
| B1 손 egui (naive, 매 프레임 `format!`) | 0.119 | 1.115 | 3.355 | 117 |
| B2 손 egui (tuned, 라벨 미리 생성) | 0.119 | 1.125 | 3.374 | 117 |
| B3 elm-magic (`render_fast`) | 0.285 | **2.809** | **8.476** | **1,088** |
| B4 elm-magic (`render` + 기록) | 0.303 | 2.933 | 8.877 | 1,088 |

- **B1/B2 = 1.00배**: 매 프레임 문자열을 만들어도 egui에서는 측정되지 않는다
  (갈레이 캐시 + 상대적으로 큰 레이아웃 비용). "최적화처럼 보이는 것"이 최적화가 아니다.
- 어댑터/B1 = **2.39배 / 2.52배 / 2.53배** (최적화 전 3.6배 → 2.5배).
  세 크기에서 비율이 안정적이라는 것은 양쪽이 같은 차수로 커진다는 뜻이다.
- 페인트 명령 구성: B1 `Text 78 + Rect 39`(화면 밖 행은 egui가 **컬링**해 명령을 안 만든다),
  B3 `Text 58 + Rect 58 + Noop 972` — 어댑터도 그리지 않지만 egui 위젯 경로가
  **자리 표시자 슬롯**을 먼저 잡아 Vec에 남는다(약 70KB/프레임).

## 6. 병목 귀속 — 1.7ms는 어디로 가는가

`hotspots.rs`의 H8이 **egui 조작 1회의 단가**(1패스 안 1,000회, ns/회)를 잰다:

| egui 조작 | 단가 |
|---|---|
| 빈 패스(기준) | 3 |
| `ui.scope` (빈 본문) | 273~293 |
| `ui.scope` (라벨 1개) | 563~588 |
| `Frame::NONE.show` | 425~452 |
| `Frame.inner_margin.show` | 422~443 |
| `ui.with_layout(가로)` | 265~278 |
| `ui.add(Label)` | 288~295 |
| `ui.add(Button)` | 488~504 |
| `ui.allocate_exact_size` | 98~101 |
| `set_height + item_spacing` | 73~76 |
| `Id::new(튜플)` | 4~5 |
| 노드당 temp 왕복(get+hover+insert) | 37 |

이 단가 × 어댑터가 행마다 만드는 조작 수로 **계산**하면 (최적화 후):

| 행 1개가 만드는 것 | 단가 × 회 | 합 |
|---|---|---|
| `Row`: **프레임+레이아웃 한 스코프**(`framed`) + `set_height` + `spacing_mut` | ~450 + 40 + 30 | ~0.52µs |
| `Text`: `Label` (+ 캐시된 해석) | 288 + 40 | ~0.33µs |
| `Button`: `Button` + 패딩 `spacing_mut` (+ 캐시된 해석) | 488 + 30 + 40 | ~0.56µs |
| intrinsic 예산: `Button` 갈레이 측정 1회 | ~300 | ~0.30µs |
| **합계(예상)** | | **~1.7µs/행** |
| **실측 차이** (B3 − B1 = 2.81 − 1.12ms) | | **1.69µs/행** |

→ 계산과 실측이 1% 안에서 맞는다. **어댑터 오버헤드의 정체는 여전히 egui `Ui` 조작 횟수**다.
손 egui(B1)는 행마다 `horizontal` + `label` + `button` ≈ 1.04µs를 쓰고, 어댑터는 여기에
`Frame`(안쪽 여백·배경) + 크기/간격 적용 + intrinsic 측정 + 해석을 **노드마다** 더한다.

최적화 전후 같은 표:

| 행 1개가 만드는 것 | 전 | 후 |
|---|---|---|
| 컨테이너 스코프 (프레임 + 레이아웃) | 425 + 265 = 690 | **~450** (한 스코프) |
| 노드마다 상태 읽기/쓰기 (temp data + 락) | ~70 | **0** (상태 규칙 없으면 생략) |
| 노드마다 해석 | 2~3회 × 70ns | 1회 + 캐시 왕복(~40ns) |
| **오버헤드 합계** | **~2.3µs/행** | **~1.7µs/행** |

## 7. 실측 — 핫스팟 (`hotspots.rs`, `rules.rs`)

| # | 재는 것 | 결과 |
|---|---|---|
| H1 | 해석 1회(규칙 6) | **70ns** (조상 1개, `:hover` 포함 동일) |
| H2 | 규칙 수 스윕 | 0→21ns, 10→56, 50→230, 200→996, 1,000→5,232 — **회당 ~5.2ns/규칙, 완전 선형** |
| H3 | 깊이 vs 평면(노드당) | 중첩이 **0.67~0.73배** — 재순회는 병목이 아니다 |
| H4 | keyed vs 위치 슬롯 | 트리 재생성 +**6~7%** (`format!("{:?}")` + 해시맵) |
| H5 | 클래스 유무 | 1.52ms → 2.91ms(min), **+92%** (해석 + `Frame`/`flex-grow` 경로 + 자리 예약) |
| H6 | 노드당 temp 왕복(3,000노드) | 0.111ms = **37ns/노드** (전체의 3%) |
| H7 | `Pass.styles` 복제 | **3,004개/패스**, 기록 켜면 +0.77ms(N=1000) |
| H8 | egui 조작 단가 | §6 표 |

스윕 해석: `rules.rs`는 1,000규칙에서 **5.27µs/회**를 실측하고, 그 값 × 3,005노드 × 3회 = **47ms**임을
출력한다 — 규칙이 많은 앱에서 캐시 이전의 어댑터가 어떻게 무너지는지를 보여준다.

## 8. 실제로 줄인 것 (0.8.3 → 다음 릴리스)

**1차 — 0.8.3** (측정으로 병목을 잡은 뒤 바로):

| 최적화 | 무엇을 없앴나 | 효과(실측) |
|---|---|---|
| `render_fast` (Pass 기록 옵트아웃) | `Pass.styles`(노드마다 `ResolvedStyle` 복제 ≈2MB memcpy) + 버튼 라벨 `String` 복제 | N=1000 4.27 → 3.48ms, N=3000 14.6 → 10.6ms |
| 스타일 해석 캐시 (프레임 단위) | 같은 노드를 한 프레임에 2~3회 해석하던 반복 | N=1000 **-0.65ms** (캐시를 끈 빌드와 직접 비교) |
| 주축 예산 프리패스 단락 | 가변 자식이 없는 컨테이너가 자식 트리를 통째로 다시 돌던 `intrinsic_main` | `PlainList`류에서 프리패스 전체 제거 |
| `Frame::NONE` → `ui.scope` | 프레임 속성이 하나도 없을 때 `Frame` 생성 | 컨테이너당 425 → 273ns |

**2차 — 다음 릴리스** (§9의 후보를 H8 단가로 계산해 하나씩 없앤 것):

| 최적화 | 무엇을 없앴나 | 효과(실측) |
|---|---|---|
| **프레임 + 레이아웃을 한 스코프로** ([`framed`]) | `Frame::show` + `with_layout`이 컨테이너마다 자식 `Ui`를 **두 번** 만들던 것. egui 0.36의 공개 부품(`Frame::total_margin`/`widget_rect`/`paint` + `UiBuilder::layout`)으로 같은 그림을 스코프 하나에 그린다 | 행마다 **-240ns** |
| **상태 추적 게이트** (`style::needs_pointer_state`) | `:hover`/`:active`/`:focus` 규칙이 하나도 없으면 노드마다 하던 temp data 읽기/쓰기 + 컨텍스트 락 3~4회를 **통째로** 생략 (`:disabled`는 요소 자체에서 오므로 무관) | 노드당 **-~70ns** → N=1000 **-0.2ms**, N=3000 **-0.6ms** |
| 포인터 상태 1회 스냅샷 | 노드마다 `pointer_hover_pos()`/`input(...)`을 다시 읽던 것 | 추적이 켜진 트리에서 노드당 락 1~2회 절약 |
| **해석 캐시 할당 재사용** (스레드 지역) | 매 프레임 `HashMap`을 새로 잡아 9,000노드에서 5MB대 새 페이지를 건드리던 것(페이지 폴트) | N=3000 **-1.7ms**, 크기 선형성 회복 |
| 캐시 조회를 `entry` 한 번으로 | 조회 후 삽입 = 해시 2회 | 노드당 ~10ns |

합계: N=1000 **4.02 → 2.78ms (-31%)**, N=3000 **≈13.5 → 8.36ms (-38%)**,
어댑터/손 egui 비율 **3.6배 → 2.5배** (세 크기에서 2.39~2.53배로 안정).

설계 원칙: **그림은 그대로**, `render`(테스트/디버깅 경로)의 계약은 유지한다.
앱은 `render_fast`를 쓰고, 스타일/버튼 전달을 확인해야 하는 곳은 `render`를 쓴다.
상태 추적 게이트는 **양방향으로** `benchmark_state`가 고정한다("없으면 안 읽고, 있으면 읽는다").

## 9. 남은 후보 (예상 효과 — H8 단가로 계산)

| 후보 | 방법 | 예상 |
|---|---|---|
| 기록 슬롯(Noop) 축소 | 화면 밖 노드는 실제 위젯을 만들지 않고 크기만 예약 (Noop 972개 ≈70KB/프레임 제거) | 1,000행당 **0.3~0.9ms** |
| intrinsic 측정 재사용 | 예산 계산에서 잰 갈레이를 그리기에서 재사용 | 1,000행당 **0.15~0.3ms** |
| 노드 temp data 배칭 | 상태 추적이 켜진 트리에서 노드마다 `memory()` 2회 → 패스 끝 1회 | 3,000노드 **0.11ms** |
| keyed 슬롯 키 최적화 | `format!("{:?}")` + `String` 해시맵 → 정수 키 맵(코어) | 트리 재생성 **-6~7%** |
| `Pass.styles` 복제 축소 | 기록 경로(테스트)도 큰 트리에서 빠르게 | N=3000 **-0.9ms** (기록 경로만) |

남은 것들은 전부 **0.1~0.9ms/1,000행** 규모다 — 다 적용해도 2.81 → 약 2.2ms
(손 egui의 약 1.9배)가 한계다. §10의 이유로 그 아래는 어렵다.

## 10. 정직한 결론 — "손 egui보다 빠른가"

**아니다, 그리고 이 구조에서는 될 수 없다.** 근거:

1. 노드마다 **최소 1개의 egui `Ui` 스코프**가 필요하다(프레임 안쪽 여백/레이아웃 전환/자리 예약).
   `ui.scope` 한 번이 273ns다 — 손 egui는 같은 일을 프레임워크
   호출 하나로 끝낸다. 노드 수만큼 곱해지는 구조적 하한이다.
2. 매 프레임 **트리를 다시 만들고**(0.56ms/3,005노드) **스타일을 해석한다**(0.21ms).
   손 egui에는 이 두 단계가 아예 없다.
3. 그래서 현실적인 목표는 "손 egui와 같다"가 아니라 **"손 egui의 2~3배 안에서,
   규칙 수가 늘어도 무너지지 않는다"**이다. 이번 릴리스는 그 목표로 **-31%**를 달성했고
   (3.6배 → 2.5배), 1,000규칙 앱에서 47ms → 약 6ms로 무너지는 지점을 없앴다.

elm-magic이 실제로 이기는 축은 성능이 아니라 **계약**이다: 컴파일타임 태그/속성 검증,
`css!` 캐스케이드, 헤드리스 계약 테스트 290개, 스냅샷, `a11y_tree`, 어댑터 2개(egui·gpui)에
같은 트리를 먹이는 이식성. 성능은 "60fps에 충분한가"로 판단해야 한다 —
이 벤치마크의 참조 화면은 **1,000행 359fps, 3,000행 119fps**다.

## 11. CI 정책

- `benchmark/`는 CI의 계약 스위트에 **포함되지 않는다**(`tests/`가 아니고, 시간은 flaky).
- CI가 지키는 것: `cargo test --workspace`(계약 290개), `cargo fmt --all --check`,
  clippy(품질 테스트 코드 경고 0), 런타임 의존성 0, 스냅샷 승인.
- 이 디렉터리의 회귀 가드는 **구조 불변식**만 단언한다 —
  트리 모양(3n+5), 패스 기록 ≤ 노드 수, 프레임 반복 시 egui temp data 불변
  (`benchmark_guard`), 상태 추적 게이트의 양방향(`benchmark_state`).
  시간 예산은 `ELM_MAGIC_PERF=1`일 때만 검사한다(로컬/릴리스 확인용).
- 한 번에 돌리는 명령: **`bash ./bench`** (옵션은 `bash ./bench --help`).
출력한다 — 규칙이 많은 앱에서 캐시 이전의 어댑터가 어떻게 무너지는지를 보여준다.
